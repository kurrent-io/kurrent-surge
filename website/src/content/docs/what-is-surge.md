title: What is Kurrent Surge
description: The design, the goals, and what changed from the v1 KurrentDB client.
---

**Nothing is inferred.** Every schema name, every codec and every mapping is something you declared
and the compiler checked, not something the SDK guessed at runtime.

That is the whole stance, and everything below follows from it.

Kurrent Surge is the .NET SDK for KurrentDB and the Kurrent Platform. It replaces the v1
`KurrentDB.Client` packages, and the EventStoreDB clients before them.

It is not a rename. The v1 client was a transport: it moved bytes to a stream and back, and everything
above that was yours to build. Surge keeps that surface and adds the layers most applications ended up
writing themselves.

## What it is for

Three things, in the order most applications need them.

**Talk to the database.** Append, read, manage streams, and reach the schema registry, secondary
indexes, connectors and node administration through one client.

**Know what your bytes mean.** A message catalog maps a CLR type to a schema name that outlives your
code, in JSON, Protobuf or Avro. Turn the registry on and the same declaration registers and validates
the shape.

**Process what arrives.** A processor owns the subscription, the checkpoints, the retries, the
batching and the partition assignment. You implement one method.

## How it is designed

### Nothing is inferred

The v1 client took a type name and wrote it on the wire. Rename the class and every consumer broke,
silently, at the next deploy.

Surge refuses to guess. A type has a schema name because you declared one, with an attribute or a
`Map` call. An append of an undeclared type throws at the client rather than writing a name you cannot
change later.

Reading is deliberately softer. A record whose schema name has no mapping comes back raw, so an
unknown type from a newer producer does not kill your subscription.

### Compile time over runtime

Catalogs, discriminated unions and Avro codecs are generated by source generators. Every publishable
package is `IsAotCompatible`, and reflection is not used to resolve a type, a codec or a mapping.

The practical effect is that a mistake surfaces when you build rather than on the first append in
production.

### One surface over two protocols

Appends run on the V2 gRPC service. Reads and stream management run on the V1 legacy service. Indexes
and connectors use V2 messages. You call one client, and the split stays an implementation detail.

### Failures have types

Every operation throws a typed exception carrying an error code. There is no result wrapper to unpack
and no single catch-all to inspect for a reason string.

```csharp
catch (StreamRevisionConflictException ex) {
    // ex.ExpectedRevision, ex.ActualRevision
}
```

### Install only what you need

There is no meta-package.

| Package | What it is |
|---|---|
| `Kurrent.Surge` | The client and the processors. What you install |
| `Kurrent.Surge.Core` | Contracts and value types. No gRPC, no transport |
| `Kurrent.Surge.Schema.Catalogs` | Message declaration and the catalog generator |
| `Kurrent.Surge.Codecs.Avro` | The opt-in Avro codec |

## What changed from the v1 client

| | v1 `KurrentDB.Client` | Kurrent Surge |
|---|---|---|
| Packages | Four, one per feature | One |
| Client | One type per feature | One client, five modules |
| Schema names | Inferred from the type name | Declared in a catalog |
| Errors | `WrongExpectedVersionException` and a catch-all | A type per failure, each with a code |
| Stream processing | Write the subscription loop yourself | A processor runtime |
| Serialization | Hand-rolled, by you | JSON, Protobuf or Avro through a codec |
| Schema registry | Not addressed | First-class, opt in |
| Secondary indexes | Not addressed | First-class |
| AOT | Reflection in the path | Source-generated, `IsAotCompatible` |
| Disposal | `IDisposable` | `IAsyncDisposable` |

Your connection strings keep working. `esdb://` and `eventstore://` still parse, and every parameter
means what it means in the other KurrentDB SDKs.

## What it is not

**Not a rewrite of your domain.** Surge serializes contracts you write. It has no opinion about
aggregates, commands or handlers.

**Not a projections engine.** Server-side projections stay on the server. Processors are a client-side
runtime for consuming streams.

**Not finished.** It is new, and it is built to grow into the rest of the platform without anyone
needing a second SDK.

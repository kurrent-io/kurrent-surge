## KurrentDB record

When a connector consumes records from KurrentDB, each record has the following structure:

```json
{
  "recordId": "string",
  "position": {
    "streamId": "string",
    "logPosition": "number",
  },
  "isTransformed": "boolean",
  "schemaInfo": {
    "Subject": "string",
    "Type": "number",
  },
  "headers": {
    "key1": "string"
  },
  "value": "object"
}
```

:::note[Details]

```json
{
  "recordId": "af0d90b7-bc4a-4220-949f-4e92df3175c2",
  "position": {
    "streamId": "user-profile-stream",
    "logPosition": 42123
  },
  "isTransformed": false,
  "schemaInfo": {
    "subject": "UserProfileUpdated",
    "type": 1
  },
  "headers": {
    "contentType": "application/json",
    "correlationId": "corr-xyz-789",
    "userId": "user-456"
  },
  "value": {
    "firstName": "John",
    "lastName": "Doe",
    "email": "john.doe@example.com"
  }
}
```

:::

Use this schema as a reference when you write filters or transformation functions. Key components:

- **`value`**: Contains the record data
- **`schemaInfo`**: Contains the event type and the subject
- **`streamId`**: Identifies the stream the record came from
- **`headers`**: Contains additional metadata, both internal properties and custom properties

### Headers

When sink connectors process records, they inject internal headers alongside any custom headers from your records. These headers carry additional metadata about the record. The `esdb-` prefix distinguishes them from user-defined headers.

The connector adds the following internal headers to each record:

| Header                        | Description                                                    |
| ----------------------------- | -------------------------------------------------------------- |
| `esdb-connector-id`           | The unique identifier of the connector processing the record   |
| `esdb-request-id`             | A unique identifier for the processing request                 |
| `esdb-request-date`           | The timestamp when the request was processed                   |
| `esdb-record-id`              | The unique identifier of the record                            |
| `esdb-record-timestamp`       | The timestamp of the record                                    |
| `esdb-record-redacted`        | A boolean value that indicates if the record has been redacted |
| `esdb-record-stream-id`       | The stream ID where the record originated                      |
| `esdb-record-stream-revision` | The revision number of the record in its stream                |
| `esdb-record-log-position`    | The global log position of the record                          |
| `esdb-record-schema-subject`  | The schema subject/name of the record                          |
| `esdb-record-schema-type`     | The schema data format type                                    |

:::caution
Some connectors send additional headers beyond the standard set listed above.
See each connector's own page for the extra headers it includes.
:::

#### User defined headers

If the connector sends headers to the sink, it prefixes user-defined headers
from your records with `esdb-record-headers-`, followed by the header name.

By default, the connector treats headers prefixed with `$` as system headers and excludes them from the output. The `"headers:ignoreSystem"` configuration setting changes that:

```json
{
  "headers:ignoreSystem": "true"
}
```

When set to `"false"`, the connector output includes system headers, those prefixed with `$`.


## Filters

All sink connectors filter records using regular expressions, JsonPath expressions, or prefixes. The connector checks the expression first as a JsonPath, then as a regex. If it is neither, the connector uses it as a prefix.

:::note
With neither `subscription:filter:scope` nor `subscription:filter:expression` set, a connector consumes
`$all`, excluding system events. With the scope set and the expression empty, a connector consumes
`$all` *including* system events. See [Configure connector](/kurrent-surge/client/connectors/settings/).
:::

### Stream ID filter

The stream ID filter matches records by their stream ID. It applies at the stream scope. For example:

```json
{
  "subscription:filter:scope": "stream",
  "subscription:filter:filterType": "streamId",
  "subscription:filter:expression": "some-stream"
}
```

The filter matches only records on the `some-stream` stream.

### Regex filters

Regular expressions are the simplest and fastest way to filter records. A regex
filter applies at the stream scope, which matches the stream ID, or at the
record scope, which matches the event type.

An example of a Regex expression:

```json
{
  "subscription:filter:scope": "record",
  "subscription:filter:filterType": "regex",
  "subscription:filter:expression": "^eventType.*"
}
```

The filter matches only records whose event type starts with `eventType`. This
filter type works at both the `stream` and `record` scopes.

### Prefix filters

You can also filter records by prefix using the following configuration:

```json
{
  "subscription:filter:scope": "stream",
  "subscription:filter:filterType": "prefix",
  "subscription:filter:expression": "prefix1,prefix2"
}
```

The filter matches only records whose stream ID starts with `prefix1` or
`prefix2`. This filter type works at both the `stream` and `record` scopes.

### JsonPath filters

JSONPath is a standardized string syntax for selecting and extracting JSON values from KurrentDB records. It follows the [RFC 9535](https://www.rfc-editor.org/rfc/rfc9535.html#name-introduction) standard. The connector applies JSONPath filters itself, and only at the record scope. They match only records with the `application/json` content type.

An example of a JsonPath filter:

```json
{
  "subscription:filter:scope": "record",
  "subscription:filter:filterType": "jsonPath",
  "subscription:filter:expression": "$[?($.value.vehicle.year==2018)]"
}
```

The filter matches only records where the year field equals 2018.

:::tip
Test your JSONPath expressions in the [JsonPath Playground](https://json-everything.net/json-path/). Copy the record JSON and check that your expressions work as expected.
:::

For the available scopes and additional configuration options, see the
[Subscription Configuration](/kurrent-surge/client/connectors/settings/#subscription-configuration) section of the settings
page.

## Transformations

Sink connectors support transformations written in JavaScript. A transformation modifies a record from a KurrentDB stream before the connector sends it to the destination. Use one to combine fields, convert values, or enrich records.

:::note
Transformations apply only to records with the `application/json` content type. The connector does not transform records with other content types.
:::

### How transformations work

A transformation is a JavaScript function, encoded in base64 and configured on the connector. The function receives a KurrentDB record that follows the [record structure](#kurrentdb-record). It can modify any part of that record before the sink processes it.

### Creating a transformation

Follow these steps to create and apply a transformation to your connector:

#### 1. Write the transformation function in JavaScript

The transformation function must meet the following requirements:

- **Function name**: Must be named `transform`
- **Parameters**: Must accept a single parameter called `record` that follows the [record structure](#kurrentdb-record)
- **Mutation style**: Must mutate the `record` object passed as its argument. Returning a new object instead throws an error.

Here's an example that combines first and last names into a full name and normalizes the email address:

```js
function transform(record) {
  const { firstName, lastName, email } = record.value;
  record.value.fullName = `${firstName} ${lastName}`;
  record.value.email = email.toLowerCase();
}
```

**Input:**

This function assumes the `record.value` is a JSON object with the following structure:

```json
{
  "firstName": "John",
  "lastName": "Doe",
  "email": "John.Doe@example.com"
}
```

**Output:**

After transformation, the record contains:

```json
{
  "email": "john.doe@example.com",
  "firstName": "John",
  "fullName": "John Doe",
  "lastName": "Doe"
}
```

#### 2. Encode the transformation function to base64

Convert your JavaScript function to a base64-encoded string. You must encode the transformation before you configure it on the connector.

#### 3. Configure the connector with the encoded transformation

Two settings turn the transformer on and supply the function:

```json
{
  "transformer:enabled": "true",
  "transformer:function": "ZnVuY3Rpb24gdHJhbnNmb3JtKHJlY29yZCkgewogIGNvbnN0IHsgZmlyc3ROYW1lLCBsYXN0TmFtZSwgZW1haWwgfSA9IHJlY29yZC52YWx1ZTsKICByZWNvcmQudmFsdWUuZnVsbE5hbWUgPSBgJHtmaXJzdE5hbWV9ICR7bGFzdE5hbWV9YDsKICByZWNvcmQudmFsdWUuZW1haWwgPSBlbWFpbC50b0xvd2VyQ2FzZSgpOwp9"
}
```

Set them when you create the connector. To add them to a connector that already exists, use
`Reconfigure`, which **replaces the settings wholesale** — send the connector's existing settings
alongside these two, or the rest are lost. See
[Managing Connectors](/kurrent-surge/client/connectors/manage/).

#### 4. Start the connector

Once configured, start the connector to process records with the transformation applied:

```csharp
await client.Connectors.Start("example-connector");
```

When you append a record to the target KurrentDB stream, the connector applies the transformation function before sending the record to the destination.

:::note
The connector adds a header property called `esdb-record-is-transformed`, set to `true`, to every record it transforms. Use that header in filters to identify or exclude transformed records.
:::


## Checkpointing

Connectors periodically store the position of the last record they processed
successfully. If the connector host restarts, each connector continues from
close to where it got to. KurrentDB stores the checkpoint in the
`$connectors/{connector-id}/checkpoints` system stream. Each connector has its
own dedicated stream for storing checkpoints.

By default, a connector with no checkpoints starts from the latest position in
the stream. The `initialPosition` property in the settings changes that
position. To start from a specific position, use [Start and stop](/kurrent-surge/client/connectors/manage/#start-and-stop) with the
`position` parameter.

## Resilience

Connectors currently support only _at least once_ delivery guarantees, so a
record may be delivered more than once. Records are delivered _in order_: record
`x` is not delivered until every preceding record has been delivered.

Most connectors retry failed writes. To see whether a connector supports
resilience, refer to the connector's individual page.

The default resilience strategy is as follows:

```d2 layout=elk
direction: right

classes: {
  box: {
    width: 190
    height: 60
  }
}

P1: Phase 1 · every 5s {class: box}
P2: Phase 2 · every 10m {class: box}
P3: Phase 3 · every hour {class: box}

P1 -> P2: after 1 min
P2 -> P3: after 1 hour
P3 -> P3: forever
```

### Automatic retries and resilience strategy

A sink connector retries a failed write automatically. Retries run at three fixed delays, each
bounded by an elapsed-time limit. Nothing doubles between attempts.

The retry process unfolds in three phases:

1. **Phase 1 – Rapid Retries**: Right after a failure, the connector retries every **5 seconds** for **up to 1 minute**. This phase covers minor issues that resolve on their own.

2. **Phase 2 – Moderate Delays**: If the failure continues, retries slow to **every 10 minutes** for the next **1 hour**. The wider spacing eases the strain on both systems.

3. **Phase 3 – Extended Delays**: If the failure persists, the final phase retries every **1 hour indefinitely**. This phase reduces unnecessary attempts, though manual intervention may eventually be required.

Each phase retries less often than the one before it.

To customize these settings, refer to the [Resilience Configuration](/kurrent-surge/client/connectors/settings/#resilience-configuration) section.

:::note
Some connectors have their own resilience mechanisms and configurations. Refer to that connector's page for details.
:::

## Data protection

KurrentDB Connectors use envelope encryption to protect sensitive configuration fields such as passwords and access tokens.

When you configure a connector, the system encrypts sensitive data using Data Encryption Keys (DEKs). It then wraps those keys with a master key based on the token you provide. KurrentDB stores the encrypted data, never the plaintext.

To see which fields are sensitive and protected, refer to each connector's [individual documentation](/kurrent-surge/client/connectors/).

### Configuring data protection

To enable data protection, configure the data protection settings in your
configuration file. Provide the encryption token either in a token file or
directly in the configuration.

:::caution
Once set, the token is permanent. Every connector needs the same token, and changing it makes all previously encrypted data inaccessible. Treat the token as a permanent secret and never change it after initial setup.
:::

#### Using a token file
```yaml
Connectors:
  Enabled: true
  DataProtection:
    TokenFile: "/path/to/token/file"
```

#### Using a token directly
```yaml
Connectors:
  Enabled: true
  DataProtection:
    Token: "<your-secret-token>"
```

:::note
If you provide both `Token` and `TokenFile`, the system uses the token file and ignores the `Token` setting.
:::

### Key vault

KurrentDB Connectors use the Surge key vault internally to manage encryption keys. Surge is KurrentDB's native key storage mechanism, and it stores encrypted keys in internal system streams. The Surge vault is the default and the only key vault currently available. The data protection framework uses it automatically, with no configuration from you.

:::caution
The data protection framework manages the Surge key vault internally. Do not configure it directly. The system handles all key vault operations automatically.
:::

Support for additional key vault options, including external key management systems, is planned for future releases.

# General C# Development
- Follow the project's own conventions first, then common C# conventions.
- Keep naming, formatting, and project structure consistent.
- Always use modern C# 14 features aggressively: extension members over static utilities, `field` keyword for property validation, span support for all buffer operations, collection expressions `[..items]` everywhere.
- Allways use records with immutable collections (ImmutableArray<T>, ImmutableHashSet<T>, ImmutableDictionary<K,V>).
- Always prefer records to classes for DTOs and value objects.
- Replace ALL static helper classes with extension members.
- Use ReadOnlySpan<T> for any method accepting buffers when possible.
- Use collection expressions `[..items]` for all collection initializations.
- Apply `field` keyword for any property needing validation or transformation.
- Vertical alignment for property declarations and fluent methods.

## Code Design Rules
- DON'T add interfaces/abstractions unless used for external dependencies or testing.
- **NEVER** wrap existing abstractions.
- **NEVER** default to `public`. Least-exposure rule: `private` > `internal` > `protected` > `public`.
- Keep names consistent; pick one style (e.g., `WithHostPort` or `WithBrowserPort`) and stick to it.
- **NEVER** edit auto-generated code (`/api/-.cs`, `-.g.cs`, `// <auto-generated>`).
- Add comments when adding public methods; use `<para>` for multiple paragraphs; never add `<returns>`, the summary must be sufficient.
- Comments explain **why**, not what.
- **NEVER** add unused methods/params.
- When fixing one method, check siblings for the same issue.
- Reuse existing methods as much as possible.
- Move user-facing strings into resource files if possible. Keep error/help text localizable.
- Use primary constructors for all services with dependency injection.
- Validate DI parameters in field initializers with null-coalescing throw.
- Default to Singleton lifetime for services (validators, handlers, regular services).
- Order class members strictly: constructors, public properties, private properties, public methods, private methods, inner types.

## Error Handling & Edge Cases
- **Null checks**: use `ArgumentNullException.ThrowIfNull(x)`; for strings use `string.IsNullOrWhiteSpace(x)`; guard early. Avoid blanket `!`.
- **Exceptions**: choose precise types (e.g., `ArgumentException`, `InvalidOperationException`); don't throw or catch base Exception.
- **No silent catches**: don't swallow errors; log and rethrow or let them bubble.

## Goals for .NET Applications

### Productivity
- Use modern C# 14 aggressively
- Prefer modern C# (file-scoped ns, raw """ strings, switch expr, ranges/indices, async streams) when TFM allows.
- Keep diffs small; reuse code; avoid new layers unless needed
- Be IDE-friendly (go-to-def, rename, quick fixes work)

### Production-ready
- Secure by default (no secrets; input validate; least privilege)
- Resilient I/O (timeouts; retry with backoff when it fits)
- Structured logging with scopes; useful context; no log spam
- Use precise exceptions; **NEVER** swallow; keep cause/context

### Performance
- Simple first; optimize hot paths when measured
- Hot paths: Process-, Handle-, Publish-, On-, When-, Send-, Dispatch-, Execute-, Calculate- methods - use Span<T>, static lambdas, ValueTask
- Stream large payloads; avoid extra allocs
- Async end-to-end; no sync-over-async
- Always favor gRPC and protobuf for service communication
- `System.Text.Json` with source generators for serialization when using JSON
- Use `Span`/`Memory`/pooling when it matters
- **Object pooling**: Use ArrayPool<T> for byte[]/char[] >256 bytes, ObjectPool<T> for objects >1KB, always return in finally blocks
- Avoid reflection; use source generators where possible
- AVoid assembly scanning at all costs; use explicit registration; consider design-time code generation for DI registration
- Publish with trimming and Native AOT where applicable
- Remove unused assemblies; exclude development dependencies

### Cloud-native / cloud-ready
- Cross-platform; guard OS-specific APIs
- Diagnostics: health/ready when it fits; metrics + traces
- Observability: ILogger + OpenTelemetry hooks
- Serilog with structured logging; no string interpolation in logs;
- 12-factor: config from env; avoid stateful singletons

# Async Programming Best Practices

- **Naming:** all async methods end with `Async` (incl. CLI handlers).
- **Always await:** no fire-and-forget; if timing out, **cancel the work**
- **Cancellation end-to-end:** accept a `CancellationToken`, pass it through, call `ThrowIfCancellationRequested()` in loops, make delays cancelable (`Task.Delay(ms, ct)`).
- **Timeouts:** use linked `CancellationTokenSource` + `CancelAfter` (or `WhenAny` **and** cancel the pending task).
- **Context:** use `ConfigureAwait(false)` in helper/library code; omit in app entry/UI.
- **Stream JSON:** `GetAsync(..., ResponseHeadersRead)`, `ReadAsStreamAsync`, `JsonDocument.ParseAsync`; avoid `ReadAsStringAsync` when large.
- **Exit code on cancel:** return non-zero (e.g., `130`).
- **`ValueTask`:** use when result often available synchronously.
- **Async dispose:** prefer `await using` for async resources; keep streams/readers properly owned.
- **No pointless wrappers:** **NEVER** add `async/await` if you just return the task

# Testing best practices

## Test structure
- Separate test project: **`[ProjectName].Tests`**
- Mirror classes: `CatDoor` -> `CatDoorTests`
- Name tests by:
    - action + expected outcome (default): `cat_door_opens_when_cat_meows`
    - condition + expected outcome: `WhenCatMeowsThenCatDoorOpens`
- Follow existing naming conventions.
- Follow AAA pattern: Arrange-Act-Assert
- Always test through **public APIs**; **NEVER** change visibility; avoid `InternalsVisibleTo`
- Use **public instance** classes; avoid **static** fields
- No branching/conditionals inside tests

## Unit Tests
- **NEVER polute a SUT with methods/capabilities only used for testing** - reconsider design if needed, and as a last resort, if programming is really what you want to do
- **NEVER test implementation details** - test behavior and outcomes only
- **NEVER use multiple unrelated assertions** - one behavior per test
- **NEVER depend on test execution order** - each test must be independent and should be able to run in any order or in parallel
- **NEVER use concrete times/dates** - use fixed test data or TimeProvider
- **NEVER create brittle tests** - avoid flakiness by isolating external dependencies
- **NEVER use hard-coded values** - use constants or test data builders
- Avoid Unicode symbols.
- Use clear assertions that verify the outcome expressed by the test name
- Assert specific values and edge cases, not vague outcomes.
- When testing multiple outcomes for one precondition, use parameterized tests
- Avoid disk I/O; if needed, randomize paths, don't clean up, log file locations.
- Avoid mocking types you own, use real implementations or interfaces
- Require tests for new/changed **public APIs**.

## Test workflow

### Run Test Command
- Look for custom targets/scripts: `Directory.Build.targets`, `test.ps1/.cmd/.sh`
- .NET Framework: May use `vstest.console.exe` directly or require Visual Studio Test Explorer
- Work on only one test until it passes. Then run other tests to ensure nothing has been broken.

## Test framework-specific guidance
**Always use the framework already in the solution** (TUnit) for new tests.

### TUnit
- Packages: `TUnit`, `Verify.TUnit`
- Test Methods: `[TestMethod]`
- Data driven tests: `[Arguments(1, 1, 2)]`

***Create a new test project***
```bash
dotnet new install TUnit.Templates && dotnet new TUnit -n "MyTestProject"
```

***Test example***
```csharp
[Test]
public async ValueTask get_greeting_async_returns_expected_greeting(CancellationToken ct) {
    // Arrange
    var name = "World";
    var expectedGreeting = "Hello, World!";
    // Act
    var actualGreeting = await GetGreetingAsync(name);
    // Assert
    await Assert.That(actualGreeting).Is.EqualTo(expectedGreeting);
}
```

### Assertions
- Use `TUnit` native assertions (prefer over Shouldly/FluentAssertions/AwesomeAssertions for new projects)
    - `Assert.That.Throws<T>()`, `Assert.That.ThrowsExactly<T>`, `Assert.That.ThrowsNothing` for exceptions. For async operations, use async delegates.
- If **Shouldly/FluentAssertions/AwesomeAssertions** are already used in a given test project, prefer them.

## Mocking
- **AVOID** mocks/Fakes at all costs
- External dependencies can be mocked. Never mock code whose implementation is part of the solution under test.
- Try to verify that the outputs (e.g. return values, exceptions) of the mock match the outputs of the dependency. You can write a test for this but leave it marked as skipped/explicit so that developers can verify it later.

## Test Data Requirements
- **Prefer Bogus** for fake/test data generation.
- Use `Bogus` providers: Person, Internet, Random, Lorem, Date, etc.
- Create test data builders using `Faker<T>` for complex objects
- Configure `Faker` rules for realistic data generation
- Provide fluent interface with `With-` methods for customization
- Default to valid state in builders
- Generate single instances with `Generate()`
- Generate collections with `Generate(count)`

## Performance Testing
- Consider BenchmarkDotNet for hot paths (not mandatory)
- Include memory diagnostics when benchmarking
